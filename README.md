# Remote control of coding-agent harnesses

How to discover, attach to, and operate many coding-agent sessions across a laptop, remote hosts and Kubernetes, with chat as one possible operator interface. These notes distinguish documented product capabilities from a proposed architecture; they are not an implementation or a benchmark.

## Questions and answers

1. **How can I centrally manage interactive and unattended agents running locally, on servers, and on Kubernetes, potentially from Slack or Zulip?** Use a small always-on coordinator as the system of record for runs, permissions, commands and artifacts, with host/Kubernetes adapters and chat adapters at its edges. Keep interactive terminal attachment separate from sending structured agent turns. Slack/Zulip should show status and request actions, not be the sole session store. Start with [the control-plane design](control-plane.md) and [chat transport and safety](chat-interface.md). This is an architectural recommendation, not a claim that a single reviewed tool supplies the whole mixed-environment solution.
2. **My actual remote use is on a phone: I keep interactive OMP sessions in tmux at my desk, but want to watch and reply to the same agents in Zulip. What can I borrow from Block's Buzz?** Keep the interactive OMP sessions as the owners; first load a bridge extension into each process (restart/resume uninstrumented hosts under the shared configuration). Mirror meaningful lifecycle updates into one Zulip topic per session and route human replies into the live session through that extension and a local bridge; use explicit delivery receipts and distinguish ordinary follow-ups from interrupts and approvals. A local bridge suffices while one computer is awake; add a hosted coordinator only when other hosts/offline routing demand it. See [the phone-first design](mobile-zulip.md) and [what Buzz actually does](buzz-pattern.md).
3. **Can I start OMP sessions by hand, attach a nearby service over ACP to read their state and map each to a Zulip topic, then create agents for new topics?** The topic-to-session mapping is sound, but `omp acp` is a separate stdio server, not a way to attach to an already-running TUI; loading its saved session into another process is not live attachment. Register each manually started TUI with an in-process OMP extension (or build a Collab guest adapter), then explicitly launch and register another interactive OMP in tmux for an authorized new topic. The earlier chat-only ACP alternative would create the two kinds of agents rejected below. See [the ACP attachment decision](acp-attachment.md).
4. **How do I launch OMP directly in ACP mode and automate new agents, while sometimes joining the same live session through OMP's sharing feature?** An ACP client can spawn `omp acp` over stdio, but that process does not host Collab; `omp join` joins an interactive OMP host. The initial answer offered separate chat-first and interactive modes, which the next question rejects. See [the ACP/Collab constraint and uniform alternative](acp-collab-modes.md).
5. **I do not want two kinds of agents. How does one uniform setup let Zulip address agents that I can also operate interactively?** Every agent is an interactive OMP host with the same globally loaded bridge extension and Collab auto-hosting, whether a human starts it or a supervisor launches it from a Zulip topic. At session start the extension registers the live session ID with a local bridge; the bridge binds it to one Zulip topic. A reply in that topic goes over local IPC into that same process through `pi.sendUserMessage`, while OMP events flow back to the topic. `omp join` is another client of that host; there is no ACP subprocess or duplicate session. See [the phone reply path](mobile-zulip.md) and [the unified host decision](acp-collab-modes.md).

## Where to start

- [A control plane for mixed-location harnesses](control-plane.md): runtime/transport choices, session ownership, lifecycle and security.
- [Chat should be an operator interface, not the agent runtime](chat-interface.md): Slack versus Zulip, event recovery, permissions and human-facing commands.
- [The same OMP session on desktop and in Zulip](mobile-zulip.md): phone-first updates, replies and the local bridge.
- [The portable pattern in Block Buzz](buzz-pattern.md): what to copy, and what not to assume of its agent harness.
- [Why ACP does not attach to a live OMP TUI](acp-attachment.md): manual registration and later topic-driven creation.
- [One interactive OMP host for chat and native guests](acp-collab-modes.md): a uniform execution model regardless of how the agent starts.

**Current recommendation:** Give every OMP launch—manual or automated—the same [globally loaded bridge extension](mobile-zulip.md) and [Collab auto-hosting](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md#sharing-every-session-automatically). The local bridge binds registered live session IDs to Zulip topics and routes replies back into those processes; native OMP/browser clients join through Collab. `omp collab list --json` can discover hosts but is not itself a Zulip reply API. No fleet coordinator is needed for one awake laptop; add one when cross-host inventory, policy or offline routing matter ([Collab discovery](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md#listing-active-local-hosts)).

**Existing integrated option, with a different scope:** kagent's `AgentHarness` is a Kubernetes resource for OpenClaw or Hermes on Agent Substrate, with kagent UI/ACP chat and documented Slack settings. Its documentation does **not** describe an OMP backend or a mixed laptop/server/Kubernetes inventory. Consider it if those documented runtimes and its substrate match your constraints; do not mistake it for generic attachment to arbitrary already-running harnesses ([concept](https://kagent.dev/docs/kagent/0.x/concepts/agent-harness/), [example](https://kagent.dev/docs/kagent/0.x/examples/agent-harness/)).
