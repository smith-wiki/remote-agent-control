# Chat should be an operator interface, not the agent runtime

**Recommendation (design inference):** Put one trusted coordinator between Slack/Zulip and a fleet of harnesses. Chat authenticates the human, carries commands and notifications, and points to durable work artifacts; it should not own an agent process, transcript, or the authoritative run state. A chat thread is a *view of* a run, not its identity.

| Surface | Verified inbound path | Useful conversation key | Operational constraint |
| --- | --- | --- | --- |
| Slack | Events/interactions via HTTPS request URL or outbound Socket Mode WebSocket; Socket Mode avoids public ingress. [Events](https://docs.slack.dev/apis/events-api/), [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) | `(team_id, channel_id, thread_ts)` for display; keep a separate immutable `run_id`. [Thread replies](https://docs.slack.dev/messaging/sending-and-scheduling-messages/#threading) | Acknowledge interactive requests in **3 seconds** and process work asynchronously; Events API retries failed deliveries. HTTPS is Slack's recommendation for the most reliable production connectivity; Socket Mode is useful behind a firewall and supports up to ten connections per app, but payloads can land on any connection. [Interactions](https://docs.slack.dev/interactivity/handling-user-interaction/#acknowledgment_response), [Events](https://docs.slack.dev/apis/events-api/#responding), [comparison](https://docs.slack.dev/apis/events-api/comparing-http-socket-mode/), [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/#connections) |
| Zulip | Bot registers an event queue, long-polls `GET /events`, and sends channel messages with a `topic`; all are outbound HTTPS from the bot. [Register](https://zulip.com/api/register-queue), [events](https://zulip.com/api/get-events), [send](https://zulip.com/api/send-message) | `(realm, channel_id, topic)` for display; keep a separate immutable `run_id`. Zulip topics serve the conversational role of threads. [Topics](https://zulip.com/help/introduction-to-topics) | Queues expire after `idle_queue_timeout_secs` of inactivity; re-register on `BAD_EVENT_QUEUE_ID` and reconcile missed commands from message history, filtering by channel/topic and durable last processed message ID. A new bot normally has no channel subscriptions. [Register](https://zulip.com/api/register-queue), [get messages](https://zulip.com/api/get-messages) |

**Recommended interaction contract (proposed, not a feature of either chat API):** `list` shows run IDs, host, state, owner and last heartbeat; `start` selects repo/base revision/harness and execution location; `attach` returns an authenticated terminal/Web UI link for an interactive run; `send` adds an ordered turn to a session; `stop` requests cancellation; `approve` resolves a particular pending action. Post concise state transitions and a final diff/PR/artifact link to a per-run thread/topic, not every token or tool log. The coordinator stores `run_id → chat address` so a moved/renamed topic cannot silently retarget a different run. Treat `stop` and `approve` as privileged operations tied to a run and an authenticated user, not as natural-language guesses.

**Delivery:** Slack Events API supplies a globally unique `event_id` and retries failed deliveries; respond promptly, then deduplicate these events by ID before creating work. Slash commands and interaction payloads need their own application-level idempotency key; do not assume they carry the Events API's `event_id`. Verify HTTPS requests against Slack's signing secret and timestamp over the *raw body*; Socket Mode's pre-authenticated WebSocket has its own envelope acknowledgment. [Event ID/retries](https://docs.slack.dev/apis/events-api/), [signature](https://docs.slack.dev/authentication/verifying-requests-from-slack/), [Socket acknowledgment](https://docs.slack.dev/apis/events-api/using-socket-mode/#acknowledge). Zulip's `last_event_id` acknowledges a queue position, but a discarded queue is not a permanent command log; use durable message IDs and the messages API for recovery. [Get events](https://zulip.com/api/get-events), [register](https://zulip.com/api/register-queue), [history](https://zulip.com/api/get-messages).

**Authority (proposed):** Platform identity is not authorization: maintain an explicit user/group → permitted repo, action and run policy, and audit who approved what. A bot token should stay in the coordinator's secret store, not every worker; a Zulip bot API key can impersonate that bot. [Zulip keys](https://zulip.com/api/api-keys).

**Decision:** For a small private deployment without public ingress, Zulip long polling or Slack Socket Mode gets a coordinator online quickly. For a larger Slack deployment with an accessible endpoint, prefer signed HTTPS ingress plus a durable queue; this follows Slack's stated reliability guidance. Neither chat transport solves discovery, ownership, session persistence, safe concurrent commands, or remote terminal attachment: these belong to the [control plane](control-plane.md).
