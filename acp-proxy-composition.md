# An ACP proxy command is not a shared chat session

**Answer.** Ready ACP-in/ACP-out components exist, but they solve different jobs. A proxy that transforms one editor–agent connection is not a multi-client session owner. A host that permits several ACP clients to attach still cannot make an arbitrary Zulip/Telegram relay display prompts typed in an editor merely by replacing its `agent_cmd`. The [broader product survey](acp-shared-session-products.md) covers shared-session hosts.

| Product | What actually ships | Live multi-client session? |

The RFD is a draft; pin compatible proxy/conductor versions. | **No:** no N-client attach, turn arbitration, or replay contract. “Conductor” orchestrates proxy processes, not a DAG of coding-agent tasks. |

For actual task orchestration, [Hydra's separate planner extension](https://github.com/smagnuso/hydra-acp-planner#readme) creates a dependency DAG via MCP tools, spawns parallel ACP worker sessions, chooses work/review agents or models, and streams progress back to the origin. [Hydra launcher mode](https://github.com/smagnuso/hydra-acp#launcher-mode) selects an agent implementation for a new session. Neither feature automatically routes every chat message among agents or supplies missing chat-session mirroring.

## Why changing `agent_cmd` is insufficient

A generic chat relay spawns its configured ACP command, sends `initialize`, calls `session/new` for its topic/thread, and tracks that ID itself. Standard `session/load`/`resume` restores state, **not** concurrent attachment ([ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup)). Hydra's pinned shim can replace that lifecycle for **one chosen session**, but one static command cannot map many topics to different already-running Hydra IDs.

**Per-agent OML proposal:** one OML instance would own one `omp acp` child and offer ACP on the other side. In that design a single-purpose bot, fixed topic, and fixed OML attach shim need **no fleet-wide session discovery or dynamic router**; selecting the instance selects the agent. A generic multi-topic bot with one static `agent_cmd` still cannot bind different topics to different OML instances by magic. Either way, forwarding its own prompts is the easy part; the bot must remain attached and render peer-originated prompts and output while idle ([OML instance design](oml-shared-sessions.md#proposed-seam-one-owner-one-agent-several-clients)).

- [`zulip-acp`](https://github.com/kfet/zulip-acp#quick-start) takes a static `agent_cmd` and owns an ACP conversation per topic. It does not implement topic→Hydra-ID discovery or all-origin idle mirroring. A fixed shim risks binding unrelated topics together.
- [`slack-acp`](https://github.com/kfet/slack-acp) likewise maps a thread to an ACP session in a common agent process; its documented permission policy auto-approves. Do not confuse its chat allowlist with safe approval arbitration for teammates.
- [`acp-connector`](https://github.com/galiprandi/acp-connector#configuration) (Telegram/Discord) accepts `agentCmd` and an optional single `sessionId`, but its [state machine](https://github.com/galiprandi/acp-connector/blob/main/DESIGN.md#state-patterns) reads updates only while processing its *own* queued prompt. It cannot display editor-originated turns while idle; its permission prompt has only the currently active chat origin.
- The reviewed ready **shared** chat frontend is [Hydra's own Slack bridge](https://github.com/smagnuso/hydra-acp-slack): it discovers daemon sessions, attaches each to a thread, renders `prompt_received` from another client, and handles permissions/reconnect. This uses Hydra REST/WebSocket APIs, not a generic substituted command. Its default watches **all** active Hydra sessions; isolate private work ([share boundary](oml-shared-sessions.md#the-operational-boundary-at-fifty)).

Other Telegram bridges also manage their own per-chat sessions. One [ignores user-message notifications](https://github.com/SuperKenVery/Telegram-ACP/blob/main/src/acp.rs#L75-L99); another offers manual [`/resume`](https://github.com/mgaitan/telegram-acp-bot#readme), not automatic attachment and all-origin observation.

## The missing contract and a falsifiable test

A usable Zulip/Telegram adapter needs: **one owner** of the agent; a fixed topic→instance binding for a single-purpose bot (or a persistent per-topic mapping for a multi-topic bot); a continuous idle subscription that renders both peer-originated user prompts and agent output without duplicate echoes; serialized prompts and one attributed permission decision; authenticated attachment, reconnect cursor/replay, and correct terminal/filesystem capability ownership. `agent_cmd` proves only that a bridge can spawn a shim, not that these behaviors exist.

**Conditional experiment, not a reported integration:** start one agent under Hydra, then configure one allowlisted Telegram chat in `acp-connector` with `agentCmd: "hydra-acp --session <ID> acp"` and no connector `sessionId`. Check that a Telegram prompt appears in the editor's **same** session and no second agent starts. While Telegram is idle, prompt in the editor; demand that both the human prompt and answer appear in Telegram. Then exercise permissions, competing turns, and connector restart/replay. The [documented prompt-scoped update loop](https://github.com/galiprandi/acp-connector/blob/main/DESIGN.md#state-patterns) predicts a failure at idle mirroring. Success in only the Telegram→agent→Telegram direction proves a command shim, **not** the requested shared conversation. A real multi-topic Zulip connector would need a Hydra-aware per-topic attach adapter.
