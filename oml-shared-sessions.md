# Keep personal tmux sessions; share only the agents that need a team

**Decision.** OML v0.2.0 is not currently a phone chat, session host, or multi-user control plane. Keep the roughly fifty personal agents in tmux. For an agent that teammates must jointly steer, start it under a shared-session host from the outset; the closest reviewed ACP option is experimental Hydra with its Slack bridge. Adding OML makes sense only if programmable policy across these sessions is valuable independently of the remote UI.

## Do not confuse three kinds of continuity

A tmux attach reaches the **same terminal process** ([tmux guide](https://github.com/tmux/tmux/wiki/Getting-Started)). An ACP `session/load` can restore prior context in another process; it does not promise concurrent control. A chat bot can create yet another session with copied thread context. Neither Hydra nor OML can retroactively attach over ACP to an already-running OMP TUI that did not start under their control ([attachment boundary](acp-attachment.md)).

| Choice | Phone | Team and tradeoff |
| --- | --- | --- |
| **tmux + mobile SSH** | Same live terminal, but terminal UX on a phone rather than chat. | Minimal change for one operator; sharing the terminal gives no per-turn identity or scoped approvals ([tmux guide](https://github.com/tmux/tmux/wiki/Getting-Started)). |
| **Claude Code Remote Control** | Same local Claude session in terminal, browser, iOS, and Android, with reconnect ([official docs](https://code.claude.com/docs/en/remote-control)). | Same-account personal control, not selective team sharing. Server mode has default capacity 32, configurable with `--capacity N`; fifty is not its assumed default. |
| **Hydra ACP + Slack** | Chat replies and desktop ACP clients address one host-owned live agent. | Teammates can prompt and approve in one Slack thread per session; queue and replay exist, but the host and bridge are experimental ([Hydra](https://github.com/smagnuso/hydra-acp), [bridge](https://github.com/smagnuso/hydra-acp-slack)). Only sessions born under Hydra qualify. |
| **Standalone chat bots** | Natural phone UX. | [Claude's Slack integration](https://code.claude.com/docs/en/slack#session-flow) creates a new cloud session, and [`zulip-acp`](https://github.com/kfet/zulip-acp) owns one ACP conversation per topic: useful for new chat-origin work, not attachment to an existing desktop agent. |
| **AHP / `ahpd`** | Needs an AHP frontend rather than a ready chat bridge. | A stronger multi-user model with sequenced actions, reconnect replay, and documented user roles ([protocol layering](https://microsoft.github.io/agent-host-protocol/guide/ahp-and-acp), [roles](https://github.com/softov/ahpd/blob/main/docs/USERS.md#roles)); more machinery than Hydra + Slack. |

Other bounded options: [Claude Code Channels](https://code.claude.com/docs/en/channels) can inject Telegram/Discord/iMessage events into an open Claude terminal in research preview, but outbound chat text is not a complete shared terminal transcript. [`opencode web` plus `opencode attach`](https://opencode.ai/docs/web/) shares one OpenCode server session between browser and terminal; documented server authentication is a single username/password, not team roles.

## The operational boundary at fifty

Fifty tmux windows still retain roughly fifty agent processes and their subprocesses; measure their actual idle cost rather than assuming a proxy will remove it. Fifty chat threads also create noise. **The stock Hydra Slack bridge watches every active Hydra session** ([configuration](https://github.com/smagnuso/hydra-acp-slack#configuration-keys)): keep private sessions outside its daemon, or add and verify an explicit per-session filter before connecting it. The Slack `AUTHORIZED_USERS` allowlist limits who may prompt or approve, not which session is visible; an empty list permits all bot-visible users ([bridge setup](https://github.com/smagnuso/hydra-acp-slack#setup)). Hydra's bearer tokens have equivalent scope, not per-person read/write RBAC ([protocol](https://github.com/smagnuso/hydra-acp/blob/master/PROTOCOL.md#authentication)). Its session log can replay updates, but the Slack bridge defaults to `BACKFILL_HISTORY=false`, so a reconnected chat may omit past turns ([bridge configuration](https://github.com/smagnuso/hydra-acp-slack#configuration-keys)).

## What OML adds—and does not

The [shipped ACP client](https://github.com/sm-th/oh-my-lisp/blob/main/src/oml/acp.clj#L230-L330) starts one local agent command over stdio, initializes it, creates sessions, sends prompts, handles permissions/cancellation, and closes. `prompt` blocks until completion and then returns collected updates; its queue is connection-wide rather than session-keyed, with a default 120-second request timeout. OML has a persistent, programmable Lisp image, but no shipped remote transport, live event subscription, session supervisor, grants, or chat frontend ([OML architecture](https://oml.sh/docs/architecture/), [ACP layer](https://oml.sh/docs/acp-architecture/)). Exposing its full eval surface to teammates would grant local code execution, not scoped session control.

A **possible future role** is an operator-programmable policy/workflow image above an existing host: name and group sessions, choose what gets shared, route notifications, and combine agent outcomes with other tools. Merely reimplementing ACP forwarding, process ownership, or a chat UI does not justify OML when Hydra or AHP already performs those jobs ([proxy comparison](acp-proxy-composition.md)).

The distinctive unmet need is a teammate steering the **same already-running, provider-independent** agent while its operator keeps using the desktop. That is a hypothesis, not measured market demand. Try a few intentionally shared sessions: count genuine desktop↔phone handoffs, teammate-authored turns, approval decisions, and replay gaps. If rare, keep the simpler personal tools; fifty terminal sessions alone do not establish a market for a new host.
