# Mirror the same tmux session into Zulip; do not move the agent into chat

The operator runs several interactive OMP TUIs in tmux—launched manually or by a local supervisor—then wants to read their progress and answer **those same agents** from a phone. A separate chat agent with another conversation would not meet this requirement.

**[PROPOSAL] Local-first topology:**

```text
Zulip topic ⇄ bot/bridge ⇄ local socket ⇄ extension ─┐
                                                   ├─ one live OMP session in tmux
OMP join/browser ⇄ Collab room ─────────────────────┘
```

The bot receives Zulip events by outbound long polling and posts by HTTPS; the phone needs no direct laptop connection ([event queue](https://zulip.com/api/register-queue), [send message](https://zulip.com/api/send-message)). The extension runs **inside** each existing OMP TUI and observes its session, message and tool lifecycle ([OMP events](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#event-surface-current-names-and-behavior)). Tmux owns the desktop terminal; Collab owns native guest access. Neither `omp acp` nor `omp collab list` is the chat input channel to that TUI ([ACP attachment distinction](acp-attachment.md)).

**[PROPOSAL] Registration makes a TUI addressable.** Install one extension in the user profile shared by manual and automated OMP launches ([extension discovery](https://github.com/can1357/oh-my-pi/blob/main/docs/extension-loading.md#1-auto-discovered-native-extension-modules)). On `session_start` it opens an owner-only local IPC endpoint and publishes `{hostInstanceId, generation, sessionId, endpoint}` plus a bearer token to a bridge-owned registry; the bridge creates or recovers that session's Zulip topic. A reply resolves `topic → exact live identity → endpoint`, and the extension checks that identity against its current session before calling `pi.sendUserMessage(text, { deliverAs: "followUp" })` **in the existing TUI process**. Its message/agent events publish progress back to the same topic, including work initiated at the desk. An authorized create action starts the **same** interactive OMP bootstrap and waits for registration—no chat-only agent class ([OMP session events](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#session-lifecycle), [message delivery](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#message-delivery-semantics)). See [the identity and session-switch fence](acp-collab-modes.md#how-a-zulip-reply-reaches-the-live-agent).

**[PROPOSAL] One Zulip topic per registered OMP session.** The topic shows host/project, useful phase changes, a question needing an answer, a short result or artifact link, and `online/busy/idle/offline` state. It should not dump token streams, raw tool output or secrets. Follow active topics on mobile; @mention the human only for blockers. Zulip supports [topics](https://zulip.com/help/introduction-to-topics), [followed-topic notifications](https://zulip.com/help/follow-a-topic) and [mobile notifications](https://zulip.com/help/mobile-notifications). Keep the exact live `(hostInstanceId, generation, sessionId) ↔ (realm, channelId, topic)` binding in the bridge; a TUI `/resume` or branch must revoke the old route rather than silently send that topic to a different conversation ([OMP session lifecycle](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#session-lifecycle)).

**[PROPOSAL] Reply and receipt:** Authorize the Zulip sender, ignore bot-originated messages, deduplicate on message ID, and default to a queued follow-up. An explicit action may steer or stop. Distinguish `seen in Zulip`, `submitted to OMP`, and `agent replied`. If the laptop sleeps, Zulip retains the reply but the agent cannot run: show offline, not a false delivery receipt. On recovery, reconcile with Zulip message history; a submission interrupted before acknowledgment is **uncertain** and must not be blindly repeated ([message events](https://zulip.com/api/get-events#message), [queue expiry](https://zulip.com/api/register-queue), [message history](https://zulip.com/api/get-messages)).

**Not every question is chat-answerable:** A normal textual question after a turn can take a follow-up. A native blocking TUI dialog needs a distinct input path. OMP's `tool_approval_requested` event is **observational**, not a remote-approval method; a plain Zulip `yes` must not authorize a pending shell operation. Phone approval needs an explicit request ID, exact action, authorized responder and expiry at a supported approval seam ([OMP tool lifecycle](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#tool-lifecycle), [approval policy](https://github.com/can1357/oh-my-pi/blob/main/docs/approval-mode.md)).

For one awake laptop, this **local** bridge suffices. A centrally hosted coordinator becomes useful later for multiple machines or durable cross-host routing. OMP keeps the full model history; Zulip is its readable operator conversation. [Buzz's routing model](buzz-pattern.md) informs the interaction without replacing Zulip. [ACP versus Collab](acp-collab-modes.md) explains how to automate the host while keeping its native OMP UI joinable.
