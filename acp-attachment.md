# Stock ACP does not attach to an already-running OMP TUI

The proposed shape is good: manually start several agents, let a nearby bridge discover their state, bind each to a Zulip topic, and later allow a topic to create a new agent. **One seam needs changing:** ACP is not currently the attachment interface to an independently running interactive OMP process.

**Rechecked against OMP main at [`04f58a9`](https://github.com/can1357/oh-my-pi/commit/04f58a91d141bb0e7c5f7679c2235945ae813057).** The interactive TUI and ACP server take [exclusive startup branches](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/main.ts#L2174-L2191). `omp acp` is a [single stdio JSON-RPC connection](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/modes/acp/acp-mode.ts#L73-L97), not an ACP listener in a separately running TUI. Its `session/load`/`resume` can reuse a session already held in that **same ACP agent's** map; otherwise it [creates another AgentSession from the saved session file](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/modes/acp/acp-agent.ts#L1250-L1339). It does not obtain the TUI's in-memory session. The ACP dispatcher [has no `session/attach` handler](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/utils/src/acp/connection.ts#L235-L264), and `omp --session` is an [alias for the persisted-session resume selector](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/cli/flag-tables.ts#L248-L252), not live attachment.

At the protocol level, `session/new` creates a distinct conversation, optional `session/load` restores one by replaying its full history, and optional `session/resume` restores its context without that replay; the current session-setup specification defines no `session/attach`, and none of those operations promises concurrent access to the same live agent process ([ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup)). A proposed multi-client extension or host layer is therefore separate implementation work, not evidence that a particular ACP agent supports live attachment: the first-party AHP comparison explicitly describes ACP as single-client and puts multi-client observation and participation in a coordinating host around it ([AHP and ACP](https://microsoft.github.io/agent-host-protocol/guide/ahp-and-acp)).

**Three distinct cases.** (1) An independently started `omp` TUI in tmux: **no stock ACP attach to its live process**. (2) An `omp acp` process: its one stdio client can control sessions it owns; a multi-client host/proxy must own that stdio from launch to attach additional clients, not arrive later via another stock OMP connection. (3) A saved session ID/file: `session/load`, `session/resume`, `--continue`, or `--session` can restore conversation state elsewhere, **not observe or control the original live process** ([ACP session map](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/modes/acp/acp-agent.ts#L1250-L1278), [CLI session opening](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/main.ts#L1150-L1199)). OMP **does** offer live access to a TUI through [Collab/`omp join`](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/commands/join.ts#L1-L39), which is a different protocol; a purpose-built in-process ACP facade could also be implemented, but neither is a stock ACP attach command.

**[PROPOSAL] One interactive execution mode, two starting points:**

| Start | Control path | Desktop consequence |
| --- | --- | --- |
| Human runs `omp` in tmux | The globally loaded extension registers that live session and accepts same-session turns over local IPC | The original TUI remains usable; an uninstrumented process is not retroactively attachable over ACP. |
| Authorized Zulip create action | A supervisor runs the same interactive `omp` bootstrap in another tmux pane, waits for the same extension to register, and binds the new session to the topic | The new agent has the same TUI, chat input path and optional Collab access as a manually started agent. |

An ACP facade for an interactive TUI is possible as a **new host-side adapter** to its live session, not through the stock `omp acp` subcommand. OMP extensions expose live events and a user-message delivery interface, and Collab exposes the running host through a separate protocol; either could support a deliberately implemented bridge. Which adapter is preferable depends on whether standard ACP clients must connect—it is not evidence that they can already do so.

OMP extensions expose session/message/tool events and `pi.sendUserMessage()` with queued `followUp` or interrupting `steer` delivery ([extension events](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#event-surface-current-names-and-behavior), [delivery](https://github.com/can1357/oh-my-pi/blob/main/docs/extensions.md#message-delivery-semantics)). A second verified live-host option is OMP Collab: with auto-hosting enabled, `omp collab list --json` exposes per-process `instanceId`, session ID, `busy` and `inputRequired`; an authenticated guest can read and prompt the original host. Its registry only discovers hosts and issues capability links, however: turning it into a Zulip adapter would require implementing a guest and carefully holding the control secret ([Collab discovery](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md#listing-active-local-hosts), [guest permissions](https://github.com/can1357/oh-my-pi/blob/main/docs/collab.md#guest-permission-model)). For a local bridge, an extension is the smaller seam.

**[PROPOSAL] Topic binding and future creation:** The bridge owns `Zulip (realm, channelId, topic) ↔ OMP sessionId`, plus process instance/generation and delivery status. Register and snapshot on each session start or switch, then publish changes; do not mistake an ACP `session/update` stream for a universal pull of a manually started agent's private state. An ordinary reply becomes a queued turn in that identified session. A new topic starts **unbound**, not a surprise agent: an explicit authorized create action selects an allowlisted project directory, launches the interactive OMP bootstrap, waits for its session registration, then atomically binds the topic and reports `starting → ready` or a failure. The Zulip topic is the conversation address; the OMP session remains the execution and model-history owner. [Phone interaction details](mobile-zulip.md) cover offline commands and approvals.
