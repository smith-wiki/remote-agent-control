# Buzz's useful pattern is chat-to-agent routing, not ACP attachment

Block's Buzz is a self-hosted chat system, not merely an ACP bridge. Its relay authenticates signed Nostr events, stores them in Postgres, and fans them out over WebSocket; Redis supports cross-instance fan-out and presence. The relay is the chat/event authority ([Buzz architecture, pinned commit](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/ARCHITECTURE.md#L1-L90)). For this project, **Zulip already fills the chat role**; copying Buzz's relay would duplicate the product rather than solve phone access.

```text
Buzz chat event → relay → buzz-acp filter/author gate → scoped queue
            → managed ACP child over stdio → session/prompt
            → agent publishes answer to Buzz using its CLI/tool
```

`buzz-acp` discovers channels for its agent identity and subscribes to matching events. Default wake-up is a mention targeting that identity, but a separate gate admits only the registered owner by default (or an explicit allowlist). A mention is not permission ([subscription and mention filter](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/config.rs#L1342-L1389), [author gate](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/lib.rs#L376-L402)). Accepted events queue with **one turn in flight per conversation scope**. The default scope is a channel; thread-scoped ACP sessions are opt-in. Separate scopes can run on different child processes ([queue](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/queue.rs#L154-L232), [scope policy](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/scope.rs#L1-L120)). A human's next message follows the same queue, so a conversation stays coherent.

Crucially, **the adapter spawns and owns the ACP process**: it opens its stdin/stdout, initializes it, creates a session, sends prompts, and replaces a dead child. It does not connect to an interactive agent previously started in tmux ([architecture](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/ARCHITECTURE.md#L672-L702), [spawn implementation](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/acp.rs#L464-L617)). Although Buzz Desktop lists `omp acp` as a preset, that command creates an ACP-mode process; it does not attach to an existing OMP TUI ([OMP preset](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/desktop/src-tauri/src/managed_agents/discovery/presets.rs#L144-L155)). See [the OMP attachment decision](acp-attachment.md).

**What users see:** Buzz puts small seen/working reactions and periodic typing into chat, not every ACP token/tool update. The agent is instructed to post a substantive reply using Buzz tools; ACP turn completion alone does not publish its answer ([progress](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/pool.rs#L4940-L5000), [answer instruction](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/base_prompt.md#L68-L78)). Generic ACP tool approvals are **not** sent to chat: the default adapter requests bypass, and any permission request that still arrives is automatically allowed once if possible. Do not copy this into a phone-operated coding agent ([configuration](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/config.rs#L454-L475), [permission handler](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/acp.rs#L1981-L2064)).

**Recovery limit:** Buzz's relay persists chat events, but `buzz-acp` states it does **not persist runner state**; it loses its child sessions after restart. Its README's claim of replaying all unprocessed mentions is not a durable processed cursor: startup normally seeds replay from process start, with an optional bounded floor ([architecture](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/ARCHITECTURE.md#L697-L702), [startup watermark](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/lib.rs#L2398-L2416)).

**[PROPOSAL] Copy the interaction, not the runtime:** Make one Zulip topic correspond to one **registered OMP session**, authorize the human separately from topic membership, serialize replies per session, publish compact `accepted → working → needs input/result` updates, and reconcile uncertain commands instead of blindly replaying them. A small **local** bridge suffices for laptop sessions regardless of how their interactive processes were launched; a hosted coordinator is a later cross-host decision. Keep approvals explicit at a supported OMP seam. [Phone interaction](mobile-zulip.md) describes the resulting flow.
