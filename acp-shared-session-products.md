# One ACP session owner can mirror direct clients into chat

**Question:** Can an ordinary ACP client and a group chat drive one live, harness-agnostic agent session while everyone sees both the client's prompts and the agent's replies?

**Yes as an architecture, and [Hydra ACP](https://github.com/smagnuso/hydra-acp) already implements the core plus Slack.** The agent runs once under a long-lived session owner. Editors connect to the owner through its ACP-agent facade; chat bots attach to that *same* session. Neither the editor nor the bot starts a second agent.

```text
ACP editor ── ACP facade ──┐
other ACP client ───────────┼── session owner ── one ACP connection ── agent
chat adapter ──────────────┘
```

The owner must record each accepted user prompt **at ingress**, including its source, before sending `session/prompt` to the agent. It broadcasts that prompt to other views and broadcasts the agent's `session/update` stream back to all views. A chat-origin message is already visible in its native thread and must not be posted a second time. One per-session turn queue, one permission arbiter, authorization, and replay after disconnect belong to the owner, not the harness. This is necessary because standard ACP defines a [point-to-point prompt/update flow](https://agentclientprotocol.com/protocol/v1/prompt-turn) but does not require a live agent to echo every user prompt as `user_message_chunk`.

**Protocol boundary:** ACP `session/load` restores and replays history; it is [not live multi-client attachment](https://agentclientprotocol.com/protocol/v1/session-setup). ACP [PR #533](https://github.com/agentclientprotocol/agent-client-protocol/pull/533) proposes `session/attach`, observer/controller roles and first-writer permission resolution, but remains an **open draft**, not an interoperability guarantee. A host may implement those semantics without modifying an ACP-speaking agent.

## What exists

| Product | Fits the shared-session requirement? | Chat and remaining gap |
| --- | --- | --- |
| [Hydra ACP](https://github.com/smagnuso/hydra-acp) | **Closest.** Its daemon owns one ACP child per session; editor, TUI, browser and bridge can attach concurrently. Prompts queue; permissions resolve once; history has replay cursors. An ordinary stdio editor runs `hydra-acp acp` or targets an existing session with `hydra-acp --session <id> acp` ([usage](https://github.com/smagnuso/hydra-acp/blob/master/README.md#running-it), [session selector](https://github.com/smagnuso/hydra-acp/blob/master/README.md#L304-L309)). | Its [Slack bridge](https://github.com/smagnuso/hydra-acp-slack) maps one session to one thread and mirrors direct-editor prompts too. **Experimental**, based on draft attachment plus Hydra-specific events; no reviewed Hydra Zulip/Telegram adapters. |
| [acp-multiplex](https://github.com/ElleNajt/acp-multiplex) | One primary ACP client and secondary Unix-socket clients share an agent; secondary-origin prompts are synthesized for the primary ([README](https://github.com/ElleNajt/acp-multiplex/blob/master/README.md#how-it-works)). | WIP, no chat adapter or durable owner. Primary-origin prompt visibility to secondaries is not established by its README. |
| [ahpd](https://github.com/softov/ahpd) + [`@ahpd/agent-acp`](https://github.com/softov/ahpd/tree/main/packages/agent-acp) | Shared host with an arbitrary ACP agent command, synchronized clients and documented [read-only roles](https://github.com/softov/ahpd/blob/main/docs/USERS.md#roles). [AHP](https://microsoft.github.io/agent-host-protocol/guide/ahp-and-acp) deliberately puts multi-client coordination above ACP. | Clients speak **AHP, not ACP**; an ordinary ACP editor requires a new ACP-to-AHP facade. No verified Zulip/Telegram/Slack adapter for this exact stack. |
| [zulip-acp](https://github.com/kfet/zulip-acp) | No: the Zulip relay owns one ACP agent session per topic; an external editor cannot concurrently attach to that live process ([README](https://github.com/kfet/zulip-acp/blob/main/README.md)). | Useful Zulip topic, sender-gating and journal design, **not** a plug-in adapter for Hydra. |
| [acp-connector](https://github.com/galiprandi/acp-connector) | No ordinary direct ACP client sharing; one bridge drives its agent ([design](https://github.com/galiprandi/acp-connector/blob/main/DESIGN.md)). | Telegram/Discord inputs serialize, but replies go to the active origin rather than a shared all-view transcript. |

**The direct-client → Slack path is implemented, not merely advertised.** Hydra emits a `prompt_received` update to other attached clients when a queued prompt becomes active, with source information in its [protocol description](https://github.com/smagnuso/hydra-acp/blob/0b2743b94e0e0850f8441a75e06c260307a1c31a/PROTOCOL.md#sessionupdate-kind-prompt_received). The [Slack projection](https://github.com/smagnuso/hydra-acp-slack/blob/fe8c3dad0daad43589c104ffa64b8537020f7933/src/acp/session.ts#L834-L890) posts this direct-client prompt before the agent's streamed reply; it filters compatibility and own-prompt echoes. Slack-origin text remains the author's native message; the [ingress](https://github.com/smagnuso/hydra-acp-slack/blob/fe8c3dad0daad43589c104ffa64b8537020f7933/src/slack/app.ts) ignores bot echoes. Teammates in that thread can thus read both sides of a live editor-driven exchange.

**Operational gaps:** Hydra's Slack bridge defaults to `BACKFILL_HISTORY=false`, so a disconnected bridge can miss turns in the *Slack thread* even though Hydra retains history; enabling full backfill risks rate limits and is not incremental recovery. Mirrored editor prompts currently omit the human's name in their Slack rendering. Set `AUTHORIZED_USERS`: its empty default allows everyone the bot sees to prompt and approve ([bridge configuration](https://github.com/smagnuso/hydra-acp-slack/blob/master/README.md#configuration-keys)). For Zulip or Telegram, build an adapter attached to the *existing owner*, not another per-chat ACP launcher; map one topic/thread to one immutable session, preserve prompt origin, avoid bot echo, replay by cursor, and separate read, prompt and approval authority. No reviewed all-in-one product meets those transports and the full visibility/recovery contract out of the box.

For an ACP-speaking OMP harness, the owner could launch `omp acp` as its sole downstream process; this needs no OMP extension or Collab dependency. It cannot attach retroactively to an independently started OMP TUI ([earlier boundary](acp-attachment.md)).
